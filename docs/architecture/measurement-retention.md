# Scheduled owner-measurement retention (AN-003)

This forward migration adds closed scheduler metadata and a versioned audited aggregate health RPC. It never installs pg_cron, creates a job, activates scheduling, or enables optional event collection. Published migration25 and its compatibility health endpoint remain unchanged. The forward producer now additionally requires verified scheduled/drained admission.

The operator must separately verify the intended First Ten database, pg_cron installation/configuration and UTC scheduling, then call the private `prepare_product_retention_job()` while collection is off. Preparation uses `cron.schedule_in_database` with **active=false**, binds one exact case-sensitive job name/database/username/schedule/command and creates a history-expiry index. It refuses an existing conflicting job rather than overwriting it. The production interval is five minutes; the five-second option is for the disposable rehearsal. Only an operator can activate the exact recorded job. Disabling collection and deactivating that exact job are distinct actions. Do not drop the extension: other jobs may depend on it.

Each actual matching running cron invocation must identify its backend PID in `cron.job_run_details`. It uses a transaction advisory lock, a two-second lock timeout, at most four passes of the existing purge with 500 rows per relation/pass (at most 8000 row deletions), a twelve-second loop budget, and a twenty-second job statement timeout. It deletes at most 500 finished history rows older than seven days for its exact recorded job. Another job's metadata is untouched. Work remaining is visible; an attempt timestamp alone never means cleanup is complete. A query cancellation rolls back and cron records failure. Other caught failures roll back the inner deletion batch and record a fixed failed outcome without source data or error text.

Health distinguishes unscheduled, inactive, unverified, failed, backlog, healthy and overdue independently of whether collection is enabled. Readiness requires the exact active job identity, a successful matching finished run, a matching recorded run ID, sane timestamps within ten minutes, a completed drain, no expired measurement rows and no overdue owned-job history. Old manual purge/25 health timestamps cannot satisfy this gate. Missing/null/mismatched/future proof fails closed. Admin identity and current database grant are refreshed; the database audits before returning the fixed aggregate DTO. No raw IDs, content, job commands, usernames, or arbitrary metadata are returned. This server helper is intentionally not mounted in shared admin UI in this scoped task.

Thirty days is the maximum **eligibility lifetime**, not a physical deletion SLA. Eligible rows stop being useful at expiry; physical removal follows a successful bounded scheduled sweep. A five-minute interval is a target, not a guarantee during outages or backlog. Seven days is likewise the history cleanup threshold, not a guaranteed physical deletion deadline. Drained time, capped backlog counts and oldest outstanding timestamps make delays visible. A globally ordered bounded sample (at most 10001 rows from each of four indexed expiry scans, then 10001 combined) reports the earliest expiry across all relations and explicitly caps large counts at 10000. History counts cap at 500.
