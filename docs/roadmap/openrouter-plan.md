# OpenRouter: low-cost AI plan for First Ten

**Checked: 2026-10-17, America/New_York.** This is a researched proposal, not an implemented configuration or a completed model evaluation. It extends the single `generateAI` gateway in [src/lib/ai.functions.ts](../../src/lib/ai.functions.ts). Current behavior and limitations are documented in [ProductSpec.md](../../ProductSpec.md); the [roadmap](../../FEATUREROADMAP_workplan.md) owns scheduling and prerequisites.

Official OpenRouter model pages and documentation were retrieved for this review. Prices below are their listed standard text rates, not a quote or a guarantee for every provider, region or future date. Direct endpoint JSON retrieval was unsuccessful in this environment; no authenticated account/provider eligibility check or paid generation was performed. Recheck model metadata, endpoint eligibility and prices before running the evaluation or releasing a routing change. Do not infer future model capabilities from a model-family name.

These roles are hypotheses, not verified quality rankings. All three candidate pages advertise JSON-schema output via `response_format`. Gemini 2.5 Flash Lite defaults to thinking disabled; Gemini 3.1 Flash Lite offers thinking levels. Model names are explicit version-family IDs rather than `latest` or automatic-router aliases, but endpoint behavior can still change.

Structured-output support is endpoint-specific. OpenRouter recommends `require_parameters: true` alongside `response_format.type: "json_schema"`; its documentation also says that enforcement varies by provider. Keep `strict: true` and independently validate the returned object. Valid JSON does not establish that a quote is real or a conclusion is supported. [Structured-output documentation](https://openrouter.ai/docs/guides/features/structured-outputs).

Before approving a route, capture its ID, provider endpoint, supported parameters, context/output limits, reasoning options, pricing, privacy eligibility and check date. The [models API](https://openrouter.ai/docs/api/api-reference/models/get-models) and [endpoint API](https://openrouter.ai/docs/api/api-reference/endpoints/list-endpoints) provide the discovery interfaces. Keep a short-lived metadata cache and an explicit last-known approved configuration; expired or unverified eligibility must not silently enable new providers.

## 2. Cost examples and what they exclude

The following are arithmetic estimates for one successful, uncached, text-only request at the listed rates:

`cost = input_tokens × input_USD_per_M / 1,000,000 + billable_output_tokens × output_USD_per_M / 1,000,000`

| Model                 | 4,000 input + 1,000 billable output | 12,000 input + 2,500 billable output |
| --------------------- | ----------------------------------: | -----------------------------------: |
| Gemini 2.5 Flash Lite |                             $0.0008 |                              $0.0022 |
| Gemini 3.1 Flash Lite |                             $0.0025 |                             $0.00675 |
| GPT-5 Mini            |                             $0.0030 |                              $0.0080 |
| Sonnet 4.5 baseline   |                             $0.0270 |                              $0.0735 |

Billable output includes reasoning where charged. These are illustrative workloads, not measured First Ten calls or promised savings. They exclude retries, separately billed tools, media, cache writes, provider/region premiums and account-level purchase fees or taxes. A cheaper token rate can lose its advantage if it needs longer reasoning, repeated regeneration or more human correction. Compare **cost per accepted, useful draft** as well as cost per request.

OpenRouter reports prompt/completion counts, reasoning/cache details and `usage.cost` in responses. Save the response generation ID and actual model, reconcile charged cost rather than relying on an estimate, and use the generation-lookup endpoint when an available ID permits later reconciliation. Current usage documentation says usage details are automatic; the old `usage.include` option is deprecated. [Usage accounting](https://openrouter.ai/docs/cookbook/administration/usage-accounting).

## 4. Proposed routing, context and failure policy

The following are initial engineering/evaluation settings to tune, not measured service guarantees.

- Keep an internal route registry keyed by `kind` and prompt/schema version. It specifies approved model/provider endpoints, input/output ceilings, reasoning settings, privacy filters, total deadline and maximum reserved cost. The client cannot submit arbitrary models, prompts or price limits.
- For short drafting, start with at most 6,000 input tokens and 2,000 total billable output tokens. For grounded work, start with at most 12,000 input and 4,000 total billable output tokens. Reserve room for system/schema overhead and model-specific reasoning. Test a supported `max_tokens` ceiling and reject truncation/empty-output responses; do not pretend a low reasoning-effort setting is an exact token cap.
- Select whole source records with stable IDs and a deterministic ordering. Replace the current character-sliced serialized JSON with token-aware context construction. Record which source IDs were included or omitted; when important evidence cannot fit, ask the founder to narrow the set or use a separately evaluated staged method. Do not silently cut a quote or discard contradictory evidence.
- Start with one primary request and at most one further application-level attempt within a 60-second total deadline; a proposed per-attempt ceiling is 25 seconds, leaving time for backoff and persistence. Use a fresh abort signal bounded by the remaining deadline. Retry only eligible transient errors with jitter and bounded `Retry-After`; do not retry authentication, insufficient funds, invalid schema, policy refusal or exhausted budget as if they were outages.
- A second attempt can be an approved fallback or a single validation-repair request, never an unlimited loop. Both consume the same request budget and attempt limit. Unknown outcomes after network loss or cancellation retain an unresolved spend reservation; cancellation does not prove that upstream work was free.
- Record `finish_reason`, model/provider, attempt count, latency, validation result and usage. Show a recoverable error and preserve the founder's previous saved draft when generation or validation fails.

Reasoning tokens are billed as output, and on most providers share the overall completion budget. They can exhaust a small limit before any visible answer appears. For Gemini 3, `reasoning.max_tokens` can map to a thinking level rather than an exact reasoning-token cap. Verify the effective total-output behavior for each selected endpoint; exclude an endpoint from a hard-capped route if that bound cannot be established. [Reasoning controls](https://openrouter.ai/docs/guides/best-practices/reasoning-tokens).

### Provider and model fallbacks

OpenRouter distinguishes provider selection from model fallback. Provider routing supports parameter requirements, allowlists, privacy filters and `max_price`. The latter specifies unit-price ceilings: `{"prompt": 0.25, "completion": 2}` means at most $0.25/M input and $2/M output, not a two-dollar request budget. [Provider routing](https://openrouter.ai/docs/guides/routing/provider-selection).

Proposed production policy: use only evaluated model/provider pairs; an economy-only route caps unit prices at $0.10/$0.40, a general route at $0.25/$1.50, and a grounded or explicitly upgraded fallback route at $0.25/$2.00. A price increase should stop the route for review, not silently expand spend. The higher fallback ceiling must be reserved before the first call. Sonnet is excluded from low-cost automatic fallbacks and needs a separate approved evaluation budget.

OpenRouter's `models` list tries models in order, can fall back on errors including moderation flags, and bills the ultimately selected model. Because First Ten needs explicit failure classification, initially prefer a small application-managed allowlist and bounded retry/fallback decision, rather than broad automatic model fallback. Log the actual result model. Never route around a refusal or relax privacy requirements to obtain an answer. [Model fallbacks](https://openrouter.ai/docs/guides/routing/model-fallbacks).

## 5. Spend control and idempotency

Application budgets must be enforced before the request, including concurrent calls; a graph of past usage is insufficient. Proposed pilot defaults for evaluation are one in-flight generation per user, three starts per minute, $0.25 per user per day and a $10 shared monthly stop. These are adjustable policy proposals, not purchase authorization or a pricing plan.

Implement these controls in a server-owned ledger with migrations and permission tests:

1. Authenticate; validate `kind`, project ownership and access to every source record. Resolve the allowed route and its worst-case cost across all permitted attempts.
2. Atomically reserve that amount against user and shared budgets. Reject unknown pricing or insufficient remaining funds. Start with total operation reservations of up to $0.02 for short drafting and $0.04 for grounded work, subject to the stricter calculated route bound; tune after measured evaluations.
3. Give each user action an idempotency key, bound to user, project, kind, source/version hash and request options. A repeated key returns the completed result or current pending state; it must not start a second provider call. A new deliberate regeneration gets a new key. Do not claim provider-side exactly-once billing unless independently verified.
4. Store estimated reservation, actual charge, generation ID, prompt/schema/model versions, attempt state and timestamps without logging private content by default. Reconcile successful charges exactly once; release unused reservation only when the outcome is known. Use an explicit unknown-charge state and reconciliation process after timeouts.
5. Make ledger rows and budgets unwritable by the browser. Test concurrent requests, duplicate submissions, failed persistence, late responses, cancellation and settlement races. Include circuit breakers for anomalous failure/cost rates.

Use OpenRouter's workspace/key guardrails as an additional shared cap, not a substitute for application-user accounting: many founders use the same server key. OpenRouter documents workspace pooled budgets and member/key guardrails as separate layers. [Spend controls](https://openrouter.ai/docs/guides/best-practices/spend-controls).

## 6. Privacy and evidence eligibility

For participant or student material, the proposed route requires approved processing choices, minimum necessary context, `data_collection: "deny"` and `zdr: true`, plus an evaluated provider allowlist. First confirm that a candidate endpoint is eligible under these combined filters. A cheap model listed in the catalog is not evidence of eligibility. If no endpoint remains, fail closed and offer manual work; do not drop a privacy filter.

ZDR is an inference-endpoint policy and does not automatically cover plugins or tools. OpenRouter says it does not retain prompt/response content unless the account opts in, while request metadata is retained. Confirm actual account settings rather than treating the documented default as an audit. Keep input/output logging off for participant data; avoid external search plugins in these routes. [ZDR documentation](https://openrouter.ai/docs/guides/features/zdr), [data collection](https://openrouter.ai/docs/guides/privacy/data-collection).

The current note-taking checkbox does not establish AI-processing or teacher-sharing permission. The privacy work must define retention/deletion, learner/teacher access, permission withdrawal and de-identification before expanding collection or sharing. Teacher routes require real authorization and RLS design, not merely a new AI `kind`.

For grounding, send stable source IDs and quoted excerpts as untrusted data. Require generated claims to distinguish observation, interpretation and uncertainty, with source references. Validate that each referenced ID was supplied and authorized, and that each purported exact quote matches the referenced excerpt under documented normalization. Reject unmatched quotes; do not silently paraphrase them into quotation marks. Deterministic checks establish reference integrity, while human review and evaluations assess whether the source actually supports the claim. Neither proves an interview occurred.

The [task registry](tasks.json) assigns AI-001–008 to this foundation and ADM-003, CLS-006, EV-005–007 and COL-004 to new product kinds. Each new kind must implement its authorized context adapter and pass its own bounded evaluation; the foundation gate does not automatically approve future kinds. The comparison should include sparse notes, contradictory interviews, irrelevant praise, hostile text inside a quote, invented citation attempts, oversized context, unsupported schema parameters, empty/length-limited output and provider outages. Require every delivered output to pass runtime shape/reference checks. The held-out corpus should contain zero invented quotes or unauthorized references; semantic conclusions still need human assessment. Do not promise a universal accuracy rate from a small suite.

Suggested route adoption rule: no critical grounding/privacy failure on the held-out set; human-rated task usefulness at least as good as the agreed baseline within a recorded tolerance; acceptable p95 latency and cost per accepted draft. For teacher feedback, a teacher must review the draft and the evaluation rubric. A model is approved only for the kinds and endpoint settings tested, not for every task in the app.

Track generated/validated/accepted/edited/rejected counts, retries, latency, cost, source-check failures and actual model. Keep those operational measures separate from the product's useful-loop and repeated-use outcomes. Do not mark founder value, teacher value or market demand as validated because an AI evaluation passes.
